# 2026-10-16 数据生产启动超时与恢复

10:45 HKT 的生产汇总停在 15,890 条 Train / 512 条 Validation。停止原因是一个 worker 在查询自己的 Slurm allocation 时，`scontrol show job` 超过 20 秒未返回；异常发生在 native evaluation 和 attempt reservation 之前。汇总器因缺失回执而触发保守的系统性错误停止，不能将该停止标签解释成已发现 native 身份漂移。

复核了冻结 native、科学配置、随机 IC target、参数设计与原 history/postprocessing 实现身份。保留原日志、预算、worker 版本和原停止快照，按真实 Slurm 终态补记这一基础设施失败。该次分配运行 22 秒、16 CPU，成本 0.09778 core-hours，已经包含在生产分配账中，不重复收费或删除失败分母；尚未生成任何 history。

worker 现在只对同一 allocation 的只读 Slurm metadata 查询超时重试一次。每次都重新执行全部身份和资源检查；其他错误不进入该重试路径，连续两次超时仍显式失败。原单参数最多一次基础设施模拟重试规则不变。7 项软件回归测试通过，这些测试不构成模拟器精度验收。

恢复作业 **2221082** 已完成：补记失败并交回现有控制器，提交数据数组 **2221086**（128 个任务、最多 16 并发）和依赖汇总 **2221087**。其中包含失败参数点的一次重试，其 theta、random seed、native、物理开关与分辨率均不改变；其余点来自原冻结 Train 设计。3 条真实数值失败继续保留，不自动重试。恢复控制作业占用 1 CPU、50 秒，另计约 0.01389 core-hours。

恢复后的数组已开始运行。新标签仍须通过原 QA 和入库检查，提交与运行不等于标签已合格。生产上限仍为 16×16=256 CPU，服从原账户与节点规则。

本次没有提交新的神经网络训练或 MCMC，没有读取 sealed labels。首轮 PCA+MLP 的精度问题仍未解决；此前开发短链完成仅代表接口功能检查完成。
